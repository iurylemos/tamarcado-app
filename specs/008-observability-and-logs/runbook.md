# Observability and Logs Runbook

## Configuration

Use one Sentry project per frontend: `client`, `collaborator`, and `backoffice`.
Set each project's DSN in that app's `VITE_SENTRY_DSN`. DSNs are public
ingestion identifiers, not credentials. Set `VITE_SENTRY_ENVIRONMENT` to
`staging` or `production`; local builds should keep it at `development`.

Use `SENTRY_ORG`, the app-specific `SENTRY_PROJECT_*` setting, and
`SENTRY_RELEASE` as non-secret release-build settings. The same release value
is embedded into browser events and uploaded source-map artifacts. When
`GITHUB_SHA` is available and no explicit release is configured, the build
uses `tamarcado@<GITHUB_SHA>`; otherwise it uses the shared package release
fallback.

`SENTRY_AUTH_TOKEN` is a restricted release-process secret. Supply it only
through the approved secret store for monitored production builds. Never put it
in a `VITE_` variable, `.env.example`, source control, browser assets, or logs.
A production build with a non-development Sentry environment and DSN requires
the token; failed uploads stop the build. Source maps are removed from Hosting
assets, including maps generated by the PWA build. Builds without Sentry
monitoring produce no public source maps.

Functions use Firebase/Google Cloud structured logging only. They require no
Sentry DSN or monitoring secret.

## Access and data handling

Grant Sentry and Cloud Logging access only to authorized operators under the
system owner's access policy. Agree retention, alerting, and volume budgets
with the system owner before production use; this repository does not establish
those policies.

Logs must be searched using operation, outcome, severity, function/resource,
and time. Do not add customer, staff, tenant, appointment, contact, message,
request, provider-payload, or credential values to diagnostic fields.
`correlationId` is an opaque server-generated UUID used only to join the
existing backend booking performance record to its notification worker record.

## Logs Explorer

Use the resource type and labels shown on the selected Functions log entry.
Generation 1-style records can be filtered with:

```text
resource.type="cloud_function"
resource.labels.function_name="createPublicAppointment"
severity>=DEFAULT
jsonPayload.operation="appointment_booking"
```

For a Cloud Run-backed Functions resource, use its service label instead:

```text
resource.type="cloud_run_revision"
resource.labels.service_name="processAppointmentNotification"
severity>=DEFAULT
jsonPayload.operation="appointment_notification"
```

Narrow either query by a time range in Logs Explorer. Where the field is
available, add `labels.execution_id="<execution-id>"` to inspect one function
execution. Join the booking and notification worker records only with
`jsonPayload.correlationId="<opaque-uuid>"`; do not substitute business IDs.

## Safe verification

Run automated frontend and Functions tests, then use only the isolated Firebase
emulator and non-production Sentry projects. A staging release must use its
own DSNs, environment name, release identity, and restricted source-map upload
secret. Verify that the frontend event is sanitized, the Functions record has
only allowlisted fields, and each Hosting `dist/` directory contains no
`.map` file or upload-token value. Do not generate smoke events in production.

The staging Sentry capture, source-map symbolication, Cloud Logging access,
and retention/alert policies require authorized external accounts and must be
verified by the system owner or release operator; they are not verified by a
local build.

## Disable reporting and rollback

To disable frontend reporting, build the release with an empty
`VITE_SENTRY_DSN` or `VITE_SENTRY_ENVIRONMENT=development`; the build then
omits source maps and does not initialize Sentry in the browser. Do not disable
or change Functions authorization, retry settings, or existing
`booking.performance` records to control monitoring.

If a staging verification or artifact check fails, stop the release and use
the previously approved release workflow to roll back. Do not deploy or change
production configuration as part of this runbook. The approved release
workflow and its restricted-secret mechanism remain dependencies of Spec 009.
